把使用者的描述當成問題線索。先找「對手」，再談功能；不要把問題線資料庫變成泛泛的 API 推薦清單。

使用者本次提供的線索：$ARGUMENTS

若本次沒有參數，從目前對話提取線索。若代理不支援 skill 目錄變數，以這份 `SKILL.md` 所在目錄作為 skill 目錄。

## 工作流程

1. 提取可觀察的症狀、舊做法的代價，以及使用者想完成的體驗。不要只抓 API 名詞，也不要把「效能不好」「很麻煩」自行補成資料沒有的具體後果。
2. 用兩到六個核心關鍵字執行檢索；找新做法或應用靈感時先篩「新能力」：

   ```bash
   python3 "${KIMI_SKILL_DIR}/scripts/search.py" --kind 新能力 --limit 3 "關鍵字一 關鍵字二"
   ```

   - 查常見錯誤、可及性或安全糾正時改用 `--kind 糾錯`；類型不確定時省略 `--kind`。
   - 可用 `--result 勝`、`--result 部分改善`、`--result 僵持`、`--group 對手組` 縮小範圍。
   - 用 `--lang en` 顯示英文欄位；查詢仍會同時搜尋中英文。
   - 已知 line ID 時用 `--id mwg:…` 直接讀完整摘要。
   - 沒有結果時，換成症狀、對手或同義詞再查一次；仍沒有就明確說資料庫沒有相符項目，不要硬湊。
3. 只挑最相關的一到三條。閱讀輸出的做法、對手、退路、戰報、支援狀態、解鎖與發想，不要只看標題或功能名。
4. 回答時依序說明：
   - **舊假設或對手**：它和使用者的哪個具體情況相符。
   - **現在可重新評估的做法**：附 line ID 與上游指南連結。
   - **現實邊界**：戰報、瀏覽器支援、退路分類與退回後果。
   - **解鎖與發想**：指出指南原文的「解鎖」；若有「發想」，標明這不是指南原文。
5. 保留資料中的證據狀態。「宣稱」表示官方指南宣稱，不是本地或跨瀏覽器實測；不可改寫成「已驗證」「一定可用」。若使用者要實作，先讀上游原文、檢查目前專案與實際支援需求，再進行修改。
6. 沒有相符線時，可以另外提供一般知識，但要與問題線檢索結果清楚分開。不要因為這個 skill 自動開 issues、提交程式碼或推薦大量功能。

## 回應原則

- 優先改變一個過時假設，而非堆出最多條線。
- 「勝」不代表適合每個專案；「僵持」仍可作為實驗靈感，但不能包裝成正式可用的保證。
- 對使用者沒有描述的後果、效能數字或瀏覽器行為，不自行補寫。
- 最後可提出一個小 demo 或驗證步驟，讓使用者判斷這條線是否真的解決自己的問題。
