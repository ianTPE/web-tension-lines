# 2026-11 抽線方式的檢索對照實驗

問題：同一批 746 條線，要把哪一部分拿去做 embedding，檢索效果最好？還是乾脆不抽線、直接用上游整份指南？

## 做法

- **語料**：`lines/` 的 746 條有效線（208 份指南、84 個對手組）。每種「抽法」就是從同一條線取出的不同文字。
- **查詢**：抽樣 150 條線（每個對手組至少一條），由 Haiku 從**上游英文原文**的引文附近段落生成兩種繁中查詢，看不到我們寫的線：
  - `symptom`：開發者描述遇到的現象
  - `goal`：開發者想做的東西
  - 查詢不得出現 API、屬性、元素名稱。見 `queries.jsonl`。
- **向量**：Voyage `voyage-3.5`，查詢用 `input_type: query`，文件用 `document`。
- **重排**：取向量前 30 名，交給 Voyage `rerank-2.5`，重排時一律用完整線文字。
- **找同形狀**：每條線當查詢，相關的定義是「同對手組、不同指南」，同指南的線不參與排名。
- **統計**：配對 bootstrap，5000 次。

重跑：`python3 make_queries.py 150`（會呼叫 claude）→ `python3 run.py`（會呼叫 Voyage，結果快取在 `.cache/retrieval/`）。完整數字見 `results.md`。

## 結論

1. **單一抽法裡，完整線最好**。只拿四槽、只拿「被什麼擋」、只拿標題，都明顯變差。描述想做的東西時，完整線比四槽高 +0.058 MRR，95% CI [+0.021, +0.097]；只有「被什麼擋」的 MRR 從 0.41 掉到 0.22。和 2026-10 shape-eval 的結論一致：切成結構槽去 embed 會丟資訊。
2. **抽線本身沒有讓「找到對的指南」變好**。完整線和不抽線（整份指南、依標題切塊）在指南層級的差距是 +0.02～0.03 MRR，CI 都跨過 0。抽線的價值在於答案能精確到「哪一個問題」，不在於提高命中率。
3. **最大的提升來自重排**。線層級 MRR 加 0.04～0.06，CI 不跨 0；指南層級的 R@1 從 0.68 升到 0.80。
4. **英文引文有沒有放進去，沒有差別**：+0.005～0.012，CI 跨 0。
5. **剩下的錯，多半是同一份指南裡的兄弟線**。重排後沒命中第一名的查詢裡，約三分之二的第一名是同指南的另一條線。
6. **找同形狀時也是完整線最好**：MAP 0.29、AUC 0.83，四槽是 0.27、0.80。但對手組本身是 LLM 看「被什麼擋」分的，這個標準答案偏向槽文字，數字要保守看。

## 限制

- 查詢是 LLM 生成的，不是真人寫的。查詢生成者（Haiku）和線的撰寫者（Opus）都是 Claude，用詞風格可能讓中文線佔便宜。整份指南是英文，屬於跨語言比對，卻仍然和中文線打平。
- 每條查詢只有一個正確答案；兄弟線算錯，但其中有些其實也答對了問題。
- 150 題，小於 ±0.03 的差距都分不出來。
