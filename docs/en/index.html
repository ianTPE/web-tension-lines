Use list markup only for real lists CorrectionWinN/A Accessibility coding guidelines · Over-announcing
Who acts
A developer (or a coding agent)
Action + object
Use <ul>/<ol> only for repeated, contiguous items; don't wrap paragraphs in a list
Blocker
Marking separate paragraphs as a list makes screen readers announce list information, so users hear confusing and redundant content (quote: "screen readers will announce list information when they encounter lists, therefore leading to a screen reader hearing potentially confusing and redundant information about the related content.")
Outcome
Win — Content that isn't a list is no longer read out as one (official claim)

List markup makes a screen reader say "list, N items" first, so misused lists become noise. The same section notes that checkboxes and radio buttons already announce their count, so wrapping them in a list duplicates it.

Sync aria-invalid with :user-invalid so errors aren't announced before input CorrectionWinWidely Accessible error announcement · Announcements mistimed or unreliable
Who acts
A developer (or a coding agent)
Action + object
Show errors with :user-invalid, and use a small script on blur/change/input/invalid to check it and set aria-invalid to match; until then, set aria-invalid="false" explicitly
Blocker
With :invalid alone, a screen reader says "Invalid entry" as soon as the user tabs into an empty required field, before any interaction (quote: "screen readers might announce \"Invalid entry\" the moment a user tabs into a required field that is currently empty.")
Outcome
Win — :user-invalid is Widely available, and the programmatic state now appears at the same moment as the visual state (official claim)

:user-invalid only affects the visuals; it doesn't touch ARIA. The guide also points out that Firefox and Safari expose an empty required field as invalid from page load, so aria-invalid can't be left unset and must be false. You still write the bridging script yourself, because there is no "UserInvalidChanged" event.

mwg:accessible-error-announcement:2 · Upstream guide · Line file · v1.0.0

Announce errors through one shared polite live region, not a live region per error CorrectionWinWidely Accessible error announcement · Announcements mistimed or unreliable
Who acts
A developer (or a coding agent)
Action + object
Put one aria-live="polite" region on the page and write "label: error" into it about 500ms after a field is left or changed; after a failed submit, move focus to the first invalid field
Blocker
Making each error message its own live region fails because it is shown rather than changed, so screen readers don't announce it reliably (quote: "a live region that is shown, rather than changed, isn't announced reliably.")
Outcome
Win — The shared region announces by changing its content, and the delay keeps it from talking over the next field (official claim)

A common pattern is putting aria-live on each error <span> and toggling its display, which announces only some of the time. The guide uses a single announcer that receives text instead. When the field is fixed, the announcer is also cleared so the old error isn't found later while reading the page.

mwg:accessible-generated-content:2 · Upstream guide · Line file · v1.0.0

Use meta text-scale so the page follows the system font size New capabilityStalemateLimited Respecting the OS text scale · User settings get ignored
Unlock · brainstormWeb pages can follow the phone's system font size (Dynamic Type) like native apps, so older or low-vision users don't have to adjust every site. Reading and documentation pages benefit most; Chrome/Edge 146+ only for now.
Who acts
A developer (or a coding agent)
Action + object
Put <meta name="text-scale" content="scale"> in <head>, size text and spacing in rem/em, and use unitless line heights
Blocker
Users set a larger system font size on iOS/Android, but mobile browsers ignore it by default and the page text stays the same (quote: "By default, mobile browsers ignore these OS-level accessibility settings to prevent legacy, fixed-pixel websites from breaking visually.")
Outcome
Stalemate — Only Chrome/Edge 146 support it; Firefox and Safari keep the default size, leaving users with manual zoom or pinch-to-zoom (official claim)

Browsers ignore the system font size to protect old fixed-px sites. The meta tag is the page declaring "my layout can take it", and only then is the system scale applied to 1rem. After opting in you must not set font-size on :root yourself, nor multiply by env(preferred-text-scale) again, or scaling is blocked or doubled.

Support <meta name="text-scale">: Limited (Chrome 146, Edge 146; not Firefox or Safari)

Fluid font sizes need a rem component, not vw alone CorrectionWinWidely Respecting the OS text scale · User settings get ignored
Who acts
A developer (or a coding agent)
Action + object
Write fluid font sizes like clamp(2rem, 1.25rem + 2vw, 4rem) so they have both a font-relative and a viewport-relative part
Blocker
With font-size: 5vw alone, text doesn't fully respond to the user's text scaling (quote: "The font size does not respond fully to user text scaling")

Pure vw sizes follow only the viewport width, so when the user enlarges text the headings don't move. The guide adds rules of thumb: keep the maximum no more than 2.5 times the minimum, and test 200% text resize and reflow at 320 CSS px wide.
