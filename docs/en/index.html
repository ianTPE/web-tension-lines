Use <install> / navigator.install() instead of beforeinstallprompt, which can only install itself New capabilityStalemateNo browser support Installing web apps · Install entry points are limited
Unlock · brainstormOne page could offer install buttons for *other* web apps, so a self-made catalog or toolbox page could install each small tool in one click. No browser supports it yet; track it for now.
Who acts
A developer (or a coding agent)
Action + object
Offer an explicit in-page install entry with the HTML <install> element or navigator.install(), including installing *other* apps (for example from an app catalog)
Blocker
The existing beforeinstallprompt can only install the current app; a catalog cannot offer installs for other apps (quote: "Unlike navigator.install(), this event cannot install a different app.")
Outcome
Stalemate — Neither new entry point is supported by any major browser yet; in practice you still rely on beforeinstallprompt or the browser's own install UI (official claim)

The guide funnels installation through browser-controlled consent UI, so sites cannot install silently. The new entry points would let a catalog install other apps in one click, but the guide states "<install> is not natively supported by any major browser yet", and the same goes for navigator.install(). Until support lands, the only fallback is the old event, which is exactly what cannot install across apps.

Support <install>: not natively supported by any major browser yet; navigator.install(): same; Web app manifest: Limited (not in Firefox)

mwg:install-web-app · Upstream guide · Line file · v1.0.0

Truncate visually with CSS instead of cutting strings in script CorrectionWinWidely Single-line text overflow · Truncation hurts accessibility
Who acts
A developer (or a coding agent)
Action + object
When a single-line label (tab, table cell, file name) is too long, truncate only on screen with text-overflow: ellipsis or a mask fade, keeping the full text in the DOM
Blocker
Cutting the string in script means screen readers, find-in-page and copy all get the mangled text (quote: "Screen readers announce the full text, find-in-page matches it, and copying copies it. This is why the string must never be cut in script.")
Outcome
Win — Truncation happens only at paint time; assistive tech, search and copy still get the full text. Ellipsis and masks are Widely available (official claim)

The common approach is to cut the string to N characters before rendering and append "…", which removes the full text from the DOM. The guide requires truncation to be visual only; to keep a tail such as a file extension, split it in the markup rather than cutting characters. Another trap: a single gradient mask also hides the focus outline ("it also hides the element's focus outline").

Support Masks: Widely (2023-12-07); Container queries (size): Widely (2023-02-14)

mwg:single-line-overflow · Upstream guide · Line file · v1.0.0

Make truncated text reachable for keyboard and touch too New capabilityPartialNewly Single-line text overflow · Only reachable by hover
Unlock · brainstormTruncated long labels (file names, tab names) can scroll to reveal the full text on hover or focus in pure CSS, with no JS width measuring and no title.
Who acts
A developer (or a coding agent)
Action + object
Scroll the text into view on :hover and :focus-visible, with scroll-driven animations controlling the fade and hint
Blocker
Relying on the title attribute alone to show the full text leaves keyboard and touch users without it (quote: "DO NOT rely on title alone: it is unreachable from the keyboard and on touch.")
Outcome
Partial — Keyboard users see the full text via focus, but touch still has no hover or focus, so the guide asks for another route (the selected item is never truncated, a detail view opens). Scroll-driven animations only just became Newly available (official claim)

title is the easiest option but only works with a mouse. The new approach scrolls the text inside its box on hover and focus, shrinking the fade as it scrolls so the end is readable. The guide also admits "Hover and focus reveal nothing on touch", so on touch the opponent is sidestepped by interface design rather than defeated by the feature. Without scroll-driven animations, the fade and hint never appear and the text is clipped with no indication; a ResizeObserver fallback is needed.

Support Scroll-driven animations: Newly (2026-10-27); Container style queries: Newly (2026-05-19)

mwg:single-line-overflow:2 · Upstream guide · Line file · v1.0.0

Move the real DOM nodes instead of faking order with CSS New capabilityPartialLimited Reordering with drag and drop · Visual order drifts from DOM order
Unlock · brainstormA playing video, a live iframe widget or a half-filled form can be moved elsewhere without resetting. Previously every move reloaded it, which made a rearrangeable live dashboard painful.
Who acts
A developer (or a coding agent)
Action + object
On drop, move the existing node once with container.moveBefore(item, ref) so visual, keyboard and reading order stay aligned
Blocker
Changing on-screen order with CSS order or flex-direction: *-reverse leaves DOM order unchanged, so Tab and screen readers follow the old order (quote: "Reorder the real children in the DOM (not via CSS order or flex-direction: *-reverse) so visual, keyboard, and reading order stay aligned.")
Outcome
Partial — Moving real nodes fixes the order mismatch, but keeping internal state needs moveBefore(), which Safari lacks; the before() fallback loses focus and other state inside items (official claim)

The cheapest drag-to-reorder is changing order: it looks right, but keyboard users jump through the old order. The guide moves the real node once on release and uses moveBefore() to keep focus and iframe state. When visual and DOM order truly cannot match in a complex layout, reading-flow is the tool, but only Chrome/Edge support it.

Support moveBefore(): Limited (Chrome 133, Edge 133, Firefox 144; not Safari); reading-flow: Limited (Chrome/Edge 137; not Firefox or Safari)

mwg:drag-and-drop · Upstream guide · Line file · v1.0.0

Show a drop marker while dragging; move only on release CorrectionWinWidely Reordering with drag and drop · Jitter during interaction
Who acts
A developer (or a coding agent)
Action + object
Keep the source item in its slot during the drag, draw a drop marker with ::before/::after, and move on pointerup
Blocker
Reordering live while dragging makes siblings shift and the list jitter (quote: "Don't reorder while the pointer moves: shifting siblings feel jittery.")
Outcome
Win — A drop marker replaces live shifting and the jitter is gone; pointer capture and fixed positioning are mature features (official claim)

Many drag implementations reorder on pointermove, so the whole list jumps every time the pointer passes an item. The guide shows only a drop line during the drag, moves once on release, and animates every move so items travel instead of jumping.

Support Pointer events: Widely

mwg:drag-and-drop:2 · Upstream guide · Line file · v1.0.0

Unlock · brainstormAfter sorting or filtering, the list animates items to their new places with a view transition while scroll, focus and playback inside each item survive. Suits lists of heavy items (embedded previews, video cards).
Who acts
A developer (or a coding agent)
Action + object
When the user changes sort order, move the existing nodes into the new order with moveBefore(), optionally wrapped in a view transition
Blocker
Creating new nodes with innerHTML or a full re-render loses focus, scroll position inside items and image state, and breaks view transitions (quote: "Recreating nodes with innerHTML or a re-render that replaces them discards focus, scroll position inside items, and image state, and it breaks view transitions, which match old and new elements by identity.")
Outcome
Partial — Moving nodes alone stops focus and scroll loss. moveBefore() is missing in Safari; the append() fallback keeps order but may lose iframe, animation or inner focus state. View transitions are Newly (official claim)

Redrawing the whole list after sorting is the usual approach, and the cost is that the button the user just clicked loses focus and a half-scrolled card jumps to the top. The guide turns sorting into "moving house" rather than "rebuilding", with animation as an optional enhancement.

Support moveBefore(): Limited (not Safari); View transitions: Newly (2025-10-14)

mwg:accordion · Upstream guide · Line file · v1.0.0

Avoid exclusive <details name> so content doesn't jump out of view CorrectionWinNewly Accordion · Side effects of a new feature
Who acts
A developer (or a coding agent)
Action + object
Allow several items open at once by default; don't use the exclusive behaviour of <details name>
Blocker
In an exclusive accordion, opening one item closes another and content shifts out of view, which seriously affects screen-magnifier users (quote: "They also can cause content to shift out of the user’s view which can cause significant problems for those using screen magnifiers.")
Outcome

<details name> only became Baseline in 2024, yet the guide advises against it. What makes this line unusual is that the opponent is not an old technique but a side effect of a new feature. When exclusivity is truly needed, the guide says to use it only as a last resort.

Collapse with ::details-content to keep find-in-page and animation New capabilityPartialNewly Accordion · Hiding or disabling locks people out
Unlock · brainstormA long page can be fully collapsed while Ctrl+F still finds and expands matches, with an opening animation. Long docs, FAQs and weekly notes no longer have to choose between collapsing and being findable.
Who acts
A developer (or a coding agent)
Action + object
Collapsed content lives in ::details-content and is hidden with content-visibility: hidden rather than display: none
Blocker
Hiding collapsed content with display: none makes it unfindable by find-in-page and its height cannot animate (quote: "While closed it is hidden with content-visibility: hidden, not display: none, which is what keeps it findable and lets its size animate.")

Once a collapsed section is display: none, Ctrl+F cannot find it. The new pseudo-element lets the browser expand the section automatically on a search hit and animate its height. Conversely, use display: none deliberately when the content should not be searchable.

Unlock · brainstormA desktop-style File/Edit/View menu bar can be built almost declaratively with popover plus anchor positioning, with menus attached to their buttons. Web tools can look and behave like desktop programs.

A developer (or a coding agent)
Action + object
Each menu in a menu bar (File/Edit/View) is a popover placed next to its trigger with CSS anchor positioning
Blocker
Without anchor positioning a popover falls back to the centered viewport position, detaching the menu from its trigger, and a centered submenu covers its parent (quote: "Never ship that for a menu: it detaches the menu from its trigger, and a centered submenu covers its parent.")

Use border-shape so borders and focus rings follow slanted segments New capabilityStalemateLimited Breadcrumbs · Focus or state indicators disappear
Unlock · brainstormSlanted, arrow or notched shapes can carry their borders and focus rings along the shape, without sacrificing accessibility to clip-path. Chromium only for now.
Who acts
A developer (or a coding agent)
Action + object
Draw slanted or arrow-shaped segments with corner-shape / border-shape, with borders and focus outlines following the shape
Blocker
Cutting shapes with clip-path also clips borders and focus outlines; forced-colors mode removes the background, so a clipped segment loses its outline (quote: "clip-path clips borders and outlines, so under the fallback use a color/background change plus negative outline-offset for focus instead of an outside outline.")
